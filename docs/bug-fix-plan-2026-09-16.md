## 3. 修復批次

### 批次 A：測試基線與 API 串接（預估 1–2 工程日）

1. 建立與本機 .env、Neon、Gemini 隔離的測試設定；固定 AI 回覆、時間與使用者。
2. 為已確認 bug 建立失敗案例，保留目前合法輸入的回歸案例。
3. INSERT 加 RETURNING id，取得 ID 並成功 commit 後才回傳。訪客和保存失敗時明確回傳保存狀態，不假裝有摘要。
4. 新完成紀錄由前端直接使用 ID；缺 ID 時提示未保存，不猜最新紀錄。舊歷史摘要入口保留。
5. doctor_schedules 先套用與其他資源 API 一致的驗證，再註冊到 main；確認訪客查詢政策與欄位相容。
6. 例外對外使用固定錯誤碼與簡短訊息，內部附 request ID 記錄；不要記錄 token、金鑰或完整問診內容。

驗收：會員完成→ID→摘要可讀；A 使用者無法讀 B 的摘要；訪客／DB 保存失敗不誤開舊摘要；門診 API 不再 404、未登入回 401、合法請求回正確資料或明確空結果。

### 批次 B：定位與醫療資源呈現（預估 1–2 工程日）

檔案：models.py、routes/diagnose.py、routes/hospitals.py、SymptomChecker.jsx、HospitalMap.jsx，必要時相關資源卡片。

1. 真實查詢座標預設 null；驗證緯經度範圍及成對出現。地圖可有預設視角，但不可作為使用者位置送給 API。
2. 位置狀態區分已定位、拒絕、失敗、手動選擇。無定位仍可問診，提供地區選擇；不顯示捏造距離或「附近」。
3. 距離缺值用 null；排序把缺值放後面，前端不顯示巨大數字，更新原本依賴 9999999 的測試。
4. 依有無醫師、班表、院所生成文案，不把科別符合等同有可掛號醫師。
5. 急症先呈現固定安全訊息。附近資源查詢另行取得或有明確逾時，不讓資料庫／定位失敗擋住警示。
6. 只用已確認急診能力的資料，不能把「最近醫院」一律當急診。專線、適用情境及文字在實作前核對官方來源，由組長確認內容。

驗收：允許／拒絕／逾時／只傳一個座標／超出範圍；無醫師、無班表、無附近院所；資源服務失敗時仍看得到急症警示。

### 批次 C：三態與跨輪安全狀態（預估 3–5 工程日，需先討論政策）

檔案：symptom_flag_extractor.py、safety_engine.py、safety_pipeline.py、models.py、diagnose.py、前端對話流程；可能新增資料庫 migration。

1. 用一致的 present / absent / unknown 型別貫穿抽取、判斷、回應與保存，保留證據文字、來源輪次、引擎版本。
2. 分開表示「已確認風險」與「資訊不足」。對與當前主訴相關的未知項做有限追問；不能對所有未知症狀問一遍，也不能將未知一律視為有症狀。
3. 已成立的阻斷條件不因其他欄位未知而解除。抽取失敗保持評估未完成，不能當低風險。
4. 建議使用伺服器端 conversation_id 與逐輪狀態。原 session_id 是完成後的歷史紀錄 ID，兩者要明確區分。
5. 每輪驗證 conversation 的擁有者，以伺服器歷史為準；role 列舉僅是格式檢查，不能防止使用者偽造 AI 歷史。
6. 同一次問診保留最高已確認風險；新一轮沒提到不等於否認。若使用者更正前述內容，記錄更正但不靜默降級；解除條件需事先定義。新問診要明確重置。
7. 多分頁／重送採 request ID 去重與版本檢查；不可用單一 Python 全域 dict 當多人、跨程序的狀態來源。
8. 急症也留下事件紀錄；資料庫失敗時仍回安全警示並明確標示未保存。若採背景工作，需承認程序中止可能遺失，可靠重試方案另估。

驗收：present→下一輪未提及；unknown→確認 absent；明確更正；抽取逾時；新對話重置；跨帳號存取；重送／同時兩輪；急症保存失敗。每個規則至少覆蓋成立、不成立、必要資料未知，以及邊界组合。

注意：以上是軟體狀態管理提案，不是已驗證的臨床規則。具體追問與升降級條件須經團隊指定的醫療內容審查；測試全綠只證明符合核定規格。

### 批次 D：資料驗證、趨勢與濫用防護（預估 2–3 工程日）

1. 統一 ProfileSchema：身高體重範圍、日期型別／不可未來日期、空字串相容、文字長度；讀取舊資料不得使整頁失效。
2. pain_level 的 null 保留未知。追查前端預設值、Request 預設值、DB 寫入、趨勢與摘要，避免只去掉 COALESCE。
3. 疼痛趨勢只使用已知分數，但無疼痛分數的問診仍計入其他適用統計；樣本不足明確顯示，不能變成分數 0。
4. 不回填舊資料中可能由預設產生的 3，除非有來源證據可區分。
5. 提議上限：單輪症狀 2,000 字、歷史每則 4,000 字、最多 40 則、總字數 20,000；先與既有對話樣本比對再定案。另限制 HTTP request body，超限可理解地回應。
6. 訪客建立、登入、問診分別限流；對 AI 呼叫設使用者及整體預算。建議起點：訪客建立每 IP 每 10 分鐘 5 次、問診每使用者每分鐘 6 次，數值待 demo 同網路情境確認。
7. 多程序使用共用儲存作配額，不宣稱記憶體計數器能跨程序保護；信任代理 IP 的範圍依部署設定。
8. CORS 用環境變數列出正式及本機來源，測試 Authorization 的 OPTIONS 預檢與實際請求。是否使用 cookie credentials 依實際登入設計決定。

驗收：超大輸入、非法 role、空值、非法生日／身高；缺值混合／全缺值趨勢；超額回 429 且不呼叫 Gemini；本機 5174 與正式來源正常，未允許來源無 CORS 授權標頭。

### 批次 E：效能、RAG 品質與維護（預估 2–4 工程日）

1. 先量測冷啟動、第一輪／後續問診耗時、DB 連線數與查詢耗時，分離 Gemini 延遲。
2. 連線池需統一借還、commit/rollback、失效連線重建與耗盡逾時。沿用 psycopg2 cursor 相容性，避免把 psycopg3 pool 直接套到既有呼叫。LLM 等待期間不長時間占用交易。
3. RAG 初始化改明確生命週期或受鎖保護的惰性初始化；失敗可以恢復，不永久快取失敗。分開應用存活與依賴就緒。
4. 醫院先以安全的候選範圍篩選，再精算距離；保留匹配排序、遠距 fallback、缺座標行為。是否新增空間索引由資料量與執行計劃決定。
5. 歷史列表分頁並減少大 JSON，詳細內容走單筆端點；同步前端載入更多。趨勢先 SQL 篩選時間窗，不能任意 LIMIT 造成分析偏差。
6. 科別快取增加 TTL 或匯入後失效；DB 暫時故障不快取為永遠空清單。
7. RAG query 使用使用者已確認的主訴／症狀／時間／否定資訊；不把模型推測變成患者事實。用固定知識庫與案例比較檢索相關性、否定症狀、長對話與延遲。
8. 清理 SELECT *、docstring、空行；統一實際 Python 支援版本與文件，不因過時 3.9 說明任意降版套件。

驗收：記錄前後相同環境測量；功能回歸不退步；連線池耗盡可恢復；RAG 初始化失敗可重試；分頁無重複遺漏；趨勢樣本範圍不被截斷。效能目標待基線後定，不先捏造改善百分比。
